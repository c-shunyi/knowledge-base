### 1. Session-Cookie 机制 (最传统、最经典)

这是最古老且至今仍在广泛使用的机制，尤其适用于传统的服务端渲染 Web 应用。

**流程：**

1. **用户登录**：客户端提交用户名和密码。
    
2. **服务器验证**：服务器验证凭据，验证通过后，在**服务器端**创建一个 Session（会话），存储用户ID、登录时间等信息，并生成一个唯一的 `session_id`。
    
3. **设置 Cookie**：服务器通过 `Set-Cookie` 响应头，将 `session_id` 返回给浏览器。
    
4. **浏览器存 Cookie**：浏览器保存这个 Cookie。
    
5. **后续请求**：浏览器每次请求同一域名下的接口时，都会**自动**通过 `Cookie` 请求头将这个 `session_id` 带回服务器。
    
6. **服务器验证 Session**：服务器根据收到的 `session_id` 去查找对应的 Session 数据，从而得知用户身份。
    

**特点：**

- **状态保存在服务端**（Server-side Session）。
    
- 安全性依赖于 `session_id` 的复杂性（防猜测）和 Cookie 的安全属性（`HttpOnly`, `Secure`, `SameSite`）。
    
- **缺点**：在分布式或微服务架构中，需要解决 **Session 共享**问题（通常使用 Redis 等集中式存储来解决）。

### 2. Token 机制 (现代主流)

为了解决 Session 机制的服务端状态问题和扩展性难题，Token 机制应运而生。其核心思想是**将状态信息加密后保存在客户端**。

#### a) JWT (JSON Web Token) - 无状态 Token

JWT 是目前最流行的 Token 方案。

**流程：**

1. **用户登录**：客户端提交用户名和密码。
    
2. **服务器验证并生成 Token**：验证通过后，服务器使用密钥生成一个 JWT。JWT 包含三部分：
    
    - **Header**：算法和类型（如 HS256, JWT）。
        
    - **Payload**：存放有效信息（如用户ID、过期时间等，不可放密码等敏感信息）。
        
    - **Signature**：对前两部分的签名，用于防止Token被篡改。
        
3. **返回 Token**：服务器将 JWT 返回给客户端（通常放在响应体中）。
    
4. **客户端存储 Token**：客户端收到后，将其存储在 `localStorage`、`sessionStorage` 或 Cookie 中。
    
5. **后续请求**：客户端每次请求需要认证的接口时，在请求头（通常是 `Authorization: Bearer <token>`）中携带此 Token。
    
6. **服务器验证 Token**：服务器验证 Signature 签名是否有效，并检查 Payload 中的过期时间，即可确认用户身份。**无需在服务端存储会话状态**。
    

**特点：**

- **无状态**：服务端不需要存储 Token，减轻了服务器压力，天然支持分布式部署。
    
- **可扩展性**：Payload 可以携带自定义信息。
    
- **缺点**：
    
    - **Token 一旦签发，在有效期内无法废止**。除非使用黑名单等额外机制，实现“登出”功能较麻烦。
        
    - Token 体积可能比 `session_id` 大，每次请求都携带，会增加带宽开销。
        

#### b) 访问令牌/刷新令牌 (Access Token / Refresh Token) - 增强版 Token

为了弥补 JWT 无法及时废止的缺陷，产生了这种双 Token 方案，OAuth 2.0 标准就采用了此模式。

**流程：**

1. **用户登录**：客户端提交用户名和密码。
    
2. **服务器返回双 Token**：
    
    - **Access Token**：生命周期很短（如 2 小时），用于访问受保护资源。
        
    - **Refresh Token**：生命周期很长（如 7 天），用于获取新的 Access Token，保存在服务端数据库或缓存中。
        
3. **客户端存储**：客户端保存两个 Token。
    
4. **API 请求**：使用 Access Token 调用 API。
    
5. **Access Token 过期**：服务器返回 401 错误。
    
6. **用 Refresh Token 获取新 Access Token**：客户端用 Refresh Token 调用一个专门的刷新接口，获取新的 Access Token。
    
7. **刷新 Token 失效**：如果 Refresh Token 也过期或被服务器加入黑名单，则用户需要重新登录。
    

**特点：**

- **安全性更高**：Access Token 有效期短，即使泄漏，影响窗口也很小。
    
- **可废止**：服务端可以通过禁用 Refresh Token 来强制用户重新认证，实现了“登出”功能。
    
- **流程更复杂**：需要客户端逻辑配合处理 Token 的刷新。

### 3. SSO (单点登录 - Single Sign-On)

SSO 不是一种具体的协议，而是一种解决方案，允许用户登录一次后，访问多个相互信任的应用系统。最常用的协议是 **OAuth 2.0** 和 **SAML**。

**核心思想**：有一个独立的**认证中心（Central Identity Provider, IdP）**。

- 用户首次访问应用A，被重定向到认证中心登录。
    
- 登录成功后，认证中心生成一个 Token 并重定向回应用A。
    
- 用户再访问应用B时，应用B发现用户未登录，将其重定向到认证中心。
    
- 认证中心发现用户已登录，直接生成Token并重定向回应用B，用户无感知。
    

**常见场景**：企业内部系统（如用一套账号登录邮箱、CRM、OA等）、“使用微信/Google/Github 登录”。

### 4. OAuth 2.0 (开放授权)

OAuth 2.0 本质上是一个**授权框架**，解决的是**授权**问题（“用户是否允许某第三方应用获取其在某资源服务器上的数据”），但它常被用作**鉴权**的基石（例如“使用微信登录”）。

**角色**：

- **资源所有者 (Resource Owner)**：用户。
    
- **客户端 (Client)**：想获取用户数据的第三方应用。
    
- **授权服务器 (Authorization Server)**：验证用户身份并颁发Token的服务器（如微信的认证服务器）。
    
- **资源服务器 (Resource Server)**：存放用户数据的API服务器（如微信的用户信息API）。
    

**流程（授权码模式最安全）**：  
用户同意 -> 客户端拿到授权码 -> 客户端用授权码换Access Token -> 客户端用Access Token访问资源服务器。

**“使用微信登录”就是利用OAuth2.0实现了鉴权**：第三方应用通过获取用户在微信的基本信息（如OpenID），来确认用户的身份。

### 总结与对比

|方式|核心原理|优点|缺点|适用场景|
|---|---|---|---|---|
|**Session-Cookie**|服务端存储状态，客户端存Session ID|成熟、易理解、可及时废止|服务器有状态，扩展性差|传统Web应用，服务器渲染页面|
|**JWT**|无状态，信息自包含在Token中|无状态、扩展性好、适合分布式|Token无法轻易废止|RESTful API、前后端分离、微服务|
|**Access/Refresh Token**|短效Access Token + 长效Refresh Token|安全性高、可废止、无状态|流程复杂|安全性要求高的应用（如银行APP）|
|**OAuth 2.0**|授权框架，委托第三方认证|标准、安全、适合第三方登录|流程复杂|第三方授权登录、开放平台|
|**SSO**|统一认证中心|用户体验好、管理方便|架构复杂|企业内部系统、生态系统产品|

**如何选择？**  
在实际项目中：

- 传统的**管理后台**可能仍用 **Session**。
    
- 前后端分离的 **Web/APP API** 接口首选 **JWT** 或 **Token** 机制。
    
- 对安全要求极高或有移动端需求，用 **Access/Refresh Token**。
    
- 需要集成第三方登录或构建开放平台，用 **OAuth 2.0**。
    
- 需要打通内部多个系统，搭建 **SSO**。
